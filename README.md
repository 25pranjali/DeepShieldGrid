# GridSentry — AI-Based Smart Grid Cybersecurity Monitoring

A final-year project prototype that detects attacks on smart-grid PMU (Phasor Measurement Unit)
data using a trained Random Forest model, explains predictions with SHAP, and displays everything
on a live-feeling web dashboard.

**Current implemented pipeline:**
```
Dataset (PMU readings) -> Flask backend -> Random Forest model -> Prediction (FDI / Normal / TSA)
        -> Confidence -> Risk score -> SQLite database -> Dashboard (frontend)
                                                        -> SHAP explanation
```

PSO/GWO/GA feature optimization, CNN-LSTM, the autoencoder anomaly module, and the full
automated-response engine are **planned/future components** — they are not implemented here.
The current model is a Random Forest classifying exactly three classes: **FDI, Normal, TSA**.

## 3. Setup — step by step in VS Code

### Step 1 — Open the project
Open the `GridSentry` folder in VS Code (**File → Open Folder**).

### Step 2 — Create a virtual environment (in a VS Code terminal)
```bash
cd backend
python -m venv venv

# Windows
venv\Scripts\activate

# macOS / Linux
source venv/bin/activate
```

### Step 3 — Install dependencies
```bash
pip install -r requirements.txt
```

If `shap` fails to install on your machine (it can be picky about compiler tools on some
Windows setups), everything else will still work — incidents are saved without SHAP
values and the SHAP page will show "no SHAP data available" instead of crashing.

### Step 4 — Initialize the database
```bash
python init_db.py
```
This creates `backend/database.db` with two demo user accounts and a few sample rows so the
dashboard isn't empty on first load.

### Step 5 — Start the backend
```bash
python server.py
```
You should see:
```
Loaded dataset with 218450 usable rows.
 * Running on http://127.0.0.1:5000
```
Keep this terminal running.

### Step 6 — Start the frontend
In VS Code's file explorer, right-click `frontend/index.html` → **Open with Live Server**.
This opens the site at `http://127.0.0.1:5500` (or similar) in your browser.

### Step 7 — Log in
Use one of the demo accounts:

| Username | Password | Role |
|---|---|---|
| `admin` | `admin123` | admin (sees the What-If Simulator too) |
| `operator` | `operator123` | user |

### Step 8 — Start the simulation
On the Dashboard, click **Start simulation**. The backend will step through the dataset one
row every 2 seconds, run the model on each row, and update the dashboard automatically. Any
row predicted as FDI or TSA creates an incident you can click into.

## 4. What each page shows

| Page | What it does |
|---|---|
| **Dashboard** | Live (simulated) PMU readings, current prediction, risk score, recent incidents table |
| **Attack Detection** | Full detail of a selected incident: predicted vs. ground-truth label, manipulated field, a *simulated* automated-response checklist |
| **Explanation (SHAP)** | Feature-contribution bar chart for the selected incident, generated by `shap.TreeExplainer` on the real Random Forest |
| **What-If Simulator** (admin only) | Manually enter the five model inputs and get a live prediction, without touching the dataset |

## 5. Important dataset note

The raw CSV stores the `time difference` column in **two different formats**:
- Normal / FDI rows: a duration string like `00:00:00.823116`
- TSA rows: a plain (sometimes negative) number of seconds, e.g. `-4.9925815...`

This happens because a Time Synchronization Attack can push the time difference far
outside a normal range. `dataset_utils.py` handles both formats — if you ever see TSA
rows disappearing from the simulation, check that conversion logic first.

`interarrival time` and `time difference` are converted to plain float seconds before
being passed to the model, since the trained model expects numbers, not duration strings.

## 6. API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/login` | Check username/password, return role |
| GET | `/api/readings/latest` | Most recent simulated (or stored) reading |
| GET | `/api/incidents` | List recent incidents (newest first) |
| GET | `/api/incidents/<id>` | Full detail of one incident, incl. predicted-vs-actual |
| GET | `/api/incidents/<id>/shap` | Stored SHAP values for one incident |
| POST | `/api/predict` | Run the model on 5 manually supplied feature values (What-If) |
| GET | `/api/dashboard/summary` | Incident counts + simulation progress |
| POST | `/api/simulation/start` | Start stepping through the dataset (`interval_seconds` optional, default 2) |
| POST | `/api/simulation/stop` | Stop the simulation |
| GET | `/api/simulation/status` | Current row index / running flag |

## 7. Risk score formula (documented, not a validated security metric)

```
if prediction == "Normal":
    risk_score = (1 - confidence) * 30        # confident Normal -> near 0
else:
    risk_score = 50 + confidence * 50         # confident attack -> near 100

Low:      risk_score < 30
Medium:   30 <= risk_score < 60
High:     60 <= risk_score < 85
Critical: risk_score >= 85
```

## 8. Current limitations

- Only FDI / Normal / TSA are detected — DoS, DDoS, Replay, Command Injection etc. are not
  implemented (no model exists for them yet).
- "Real-time" is a simulated replay of the historical dataset, not a live SCADA/PMU feed.
- Login is a simple demo token, not production-grade authentication.
- The automated-response engine is a static, simulated checklist — it does not control any
  real equipment.
- Admin/user role gating currently only hides the What-If Simulator nav item; other pages
  are visible to both roles.
